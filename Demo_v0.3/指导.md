## 3. 与数贸协议需求的差距

### 3.1 模块接入差距
- `utils/data_protocol.c` 未加入 `xmake.lua` 的 `add_files(...)`，当前默认构建不会编译该模块。
- 代码中没有主机消息接收状态机（`S/E/P` 解析与应答）。

### 3.2 数据组织差距
- 当前任务间共享是“快照”（latest value），不是“公共环形缓存区历史数据”。
- 尚未建立“按查询逐包回传”的消息队列/记录队列。
- 尚未建立峰值触发事件与其上传数据组织。

### 3.3 协议一致性差距（`data_protocol` 内部）
- Base64 编解码使用了 `=` padding 且解码要求长度 `%4==0`，与需求中“末尾可 2/3 字符”不一致。
- 报文数据字段编码实现与需求定义存在偏差风险（建议重构为按字段位宽写入，而不是松散字节拼装）。
- 未完整覆盖查询-续传-结束（`i/m/h/n`）语义、重发（`E`）语义、参数确认（`q`）语义。

## 4. 可复用基础：ringbuffer

你提到的 `utils/ringbuffer.*` 可以直接复用，建议如下：

1. 用途分层
- `record_ring`：存放“采集记录对象（结构体）”。
- `proto_tx_ring`：存放“已构建好的待发送协议帧”。

2. 使用建议
- 采集侧写入使用 `ringbuffer_put_force`（保证新数据不丢，允许覆盖最旧数据）。
- 协议发送侧读取使用 `ringbuffer_get`（按查询节奏消费）。
- 记录对象尽量定长，减少内存碎片与复杂度。

3. 注意事项
- 当前 ringbuffer 实现更偏“字节流环形队列”，如果直接存结构体，建议包装一层 record queue API（写入/读出固定长度块，统一检查边界）。
- 若中断和任务并发访问同一个 ringbuffer，需要统一在同一上下文操作或加轻量临界区保护。

## 6. 分阶段实施计划（建议）

### 阶段 A：协议库校准（先做）
目标：让 `data_protocol` 单体与 `数贸Demo.txt` 一致。

任务：
1. 修正 Base64（支持 2/3/4 字符尾部解码，不使用 `=`）。
2. 统一 CRC24Q 校验输入范围（`# + msg + seq + content`）。
3. 重做 `i/h` 内容字段打包/解包，严格按位宽实现。
4. 补最小测试（可先做主机侧脚本测试）。

交付标准：
- 给定样例输入，编码输出稳定且可互解。
- 错帧/CRC 错误能被可靠拒绝。

### 阶段 B：数据存储链路
目标：实现“公共环形缓存区存储采集数据”。

任务：
1. 定义记录结构：时间、温湿度、峰值/加速度片段、标记位。
2. 在采样任务中按策略入队（普通采样 + 峰值事件）。
3. 提供“取下一条待上传记录”的 API。

交付标准：
- 在不接协议的情况下，可打印验证 ring 中记录完整、顺序正确、覆盖策略生效。

### 阶段 C：协议任务接入
目标：主机可通过 `S/E/P` 与设备交互。

任务：
1. 从 CDC 读字节流，按 `#...$` 提帧，调用 `parse_frame`。
2. `S`：返回 `n/m/i/h`（按队列与分片状态机）。
3. `E`：重发最近待确认分片（消息号不变）。
4. `P`：参数落地并回复 `q`（内容回显）。

交付标准：
- PC 连续发送 `S` 能完整拉取一条长记录直到 `h`。
- 插入 `E` 能重发同一分片，序号符合要求。

### 阶段 D：稳定性与联调
目标：达到可演示状态。

任务：
1. 压测帧长（USB CDC 64 字符上限场景）。
2. 注入异常：断包、错 CRC、超时重试。
3. 完善日志级别和统计指标。

交付标准：
- 连续运行稳定，无死锁/任务饿死。
- 异常链路可恢复。

## 7. 开发优先级（强烈建议）

1. 先修协议库一致性，再做任务接入。
2. 先打通 `P -> q`（最简单闭环），再做 `S/E` 查询链路。
3. `i/h/m/n` 从最小可用实现开始：
- 第一版可先只上传温湿度 + 少量加速度点；
- 第二版再扩展完整分片与更高吞吐。

## 9. 下一步建议

建议下一步直接做“阶段 A + 阶段 C 最小闭环”：
- 先让主机发 `P`，设备回 `q`；
- 再让主机发 `S`，设备先回 `n`（无数据）；
- 最后接入 ring 数据后升级到 `i/h` 分片上传。

这样可以最快形成可联调骨架，后续只是在骨架上加数据内容和吞吐优化。
