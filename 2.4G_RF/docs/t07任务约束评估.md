# T07 任务约束评估（已被 v2.1 时间戳决策修订）

本文用于评估 `docs/t07任务约束` 中“全网时间对齐与显式传播”方案在当前协议与工程中的可行性，并将结论收束到 `T07`。

> 2026-05-03 更新：本文件的早期结论建立在“必须保持 `A` 帧 6 条确认容量”这一前提上。最新 `docs/软件设计文档.md` 已将时间戳降级为 `Content` 内数据字段，并接受 `A` 帧确认容量下降到 `5` 条。因此本文不再作为阻断 `LMT_A` 落地的依据，仅保留早期风险分析供参考。

## 1. 总结结论

- **语义目标正确**：希望所有信标以网关统一时间为准结束组网，而不是依赖“本地首次观测时刻”，这与 `003.pdf` 的“组网时间结束后停止继续组网”方向一致。
- **直接落地前提已改变**：早期认为 `4B Epoch` 与 6 条确认容量硬冲突；最新协议已接受 `LMT_A(4B)` 占用 `Content[0..3]`，并将确认容量调整为 `5` 条。
- **协议适配程度：已完成主协议迁移，当前进入 `T07` 后续验证与收口阶段**。
- **T07 收束策略**：
  1. 当前主线短期保留“轻量本地结束时刻继承”实现，避免打断已验证双板链路；
  2. `LMT_A` 内容字段迁移已完成（`T11`）；
  3. 当前回到 `T07` 继续复核全网统一结束时刻与多网关锁定策略。

## 2. 早期为什么不能直接落地

### 2.1 A 类帧 Payload 已经满载

早期评估时的协议固定：

- 单帧固定 `32B`
- `payload` 固定 `24B`
- 单个 `ID` 打包固定 `4B`

当前 `A` 帧布局已经打满：

1. **网关确认帧**
   - `A V=0`
   - 最多 `6` 个确认 ID
   - `6 * 4 = 24B`
   - **没有剩余空间**

2. **未确认信标上行回应帧**
   - 第 `1` 个 `4B`：上级 ID + `Flag`
   - 其余最多 `5` 个 `4B`：对子级确认
   - `4 + 5 * 4 = 24B`
   - **同样没有剩余空间**

3. **已确认信标广播帧**
   - 最多 `6` 个 `4B` 确认 ID，或第一个槽位回填 `Flag=6` 的已确认上级
   - 也默认占满 `24B`

因此，如果在旧前提下强行加入 `4B Epoch`：

- 网关确认帧容量会从 `6` 条降为 `5` 条；
- 未确认信标回应帧会从“`1` 条上级 + `5` 条下级确认”降为“`1` 条上级 + `4` 条下级确认”；
- 已确认信标广播帧也会丢失 `1` 个确认槽位。

这一风险已经通过最新协议裁决转化为显式容量调整：组网确认从 `6` 条改为 `5` 条，已确认节点广播从“上级 + 5 条下级确认”改为“上级 + 4 条下级确认”。

### 2.2 该方案不是“实现细节调整”，而是“协议布局变更”

约束书里的这些动作：

- 增加 `ADHOC_PAYLOAD_EPOCH_IDX`
- 修改 Reply List 打包偏移
- 要求 Beacon 一律用 `Epoch + window` 作为结束时刻

本质上已经不是状态机优化，而是 **A 类帧 Payload 重新分配**。该协议层确认已经在最新 `docs/软件设计文档.md` 中发生，因此后续不再把它当作单纯状态机优化，而是作为 `T11` 帧/载荷迁移执行。

## 3. 与当前实现的适配程度

### 3.1 已经适配的部分

- 网关侧已有 `network_window_us`
- 网关侧已有 `gateway_network_start_us / gateway_network_end_us`
- 信标侧已有 `candidate.network_end_us`
- 信标侧已有“方向结束时刻继承 + 到期锁定停发”

也就是说：

- **时间窗控制机制已经具备**
- **差的不是状态机能力**
- **差的是如何在不破坏现有 A 帧载荷的前提下显式传播全网统一时间**

### 3.2 当前实现与新约束的差异

当前实现：

- 使用“本节点首次观测该方向”的本地时间推导 `network_end_us`
- 不扩展 `A` 帧字段
- 不改变 `6` 条确认容量

新约束方案：

- 使用网关广播的显式 `Epoch`
- 所有节点都以 `Epoch + window` 对齐结束时刻
- 需要侵入 `A` 帧 `payload`

所以它与当前实现不是“参数不同”，而是“载荷模型不同”。

## 4. 风险评估

### 4.1 高风险：确认容量下降

这是早期最大的阻断项。现在该风险已经转化为已接受的容量调整：`A` 帧确认能力下降到 `5` 条，仍需重点验证以下影响：

- 网关 `T2/T5` 收口能力
- 多下级同时确认效率
- 既有状态机与测试假设

### 4.2 中风险：主网关切换语义

约束书提出：

- 信标应跟随 `network_end_us` 最晚的网关，或至少对齐主网关 Epoch

这和当前 `T07` 的锁定规则存在耦合：

- 当前优选策略是“强信号 + 低级别 + 小 gateway_no + 小 upstream_id”
- 一旦已响应某个方向，后续只响应该方向

如果未来引入显式 Epoch，就必须先明确：

1. 时间对齐是否服从“已选主方向”；
2. 是否允许“只更新时间、不切换方向”；
3. 是否允许“时间更晚但信号更差”的网关覆盖当前锁定方向。

这些都还不是纯编码问题，而是协议判定问题。

### 4.3 低风险：`uint32_t ms` 回绕

这点可以接受：

- 若使用“相对网关启动的毫秒数”，`49.7` 天回绕对 `30s` 组网窗完全足够；
- 因此回绕不是当前阻断点。

## 5. 推荐结论（收束到 T07）

### 5.1 `T11` 迁移结果（已完成）

原因如下：

- 最新文档已明确 `LMT_A(4B)` 是 `A` 帧 `Content` 内数据字段；
- 确认容量下降到 `5` 条已经成为目标协议的一部分；
- `Content` 内 `LMT_A/LMT_D` 迁移已完成，当前进入 `flag=7` 确认语义与驱动协同收口阶段。

### 5.2 从候选项转为后续收口主线

建议把 `docs/t07任务约束` 收束为：

- **主线方案：`Content[0..3]=LMT_A`**
- 当前状态：**协议已接受，`T11` 迁移已完成**

### 5.3 当前 T07 主线继续保持

当前路线调整为：

1. 保持 `32B` 固定帧；
2. 恢复帧壳 `Content(24B)`，取消独立帧级 timestamp；
3. `A` 帧使用 `LMT_A(4B)+最多5条确认`；
4. 保持当前“本地方向结束时刻继承 + 到期锁定停发”实现作为过渡，并在现有 `LMT_A` 基线上继续收口统一时间推导。

## 6. 若后续一定要做显式传播，必须先二选一

只能在以下方向里选其一：

### 方案 A：修改协议载荷布局（已选择）

- 接受 `A` 帧确认能力下降；
- 同步修改设计文档与验证标准；
- 明确这是对 `003.pdf` 的工程化偏移。

### 方案 B：修改协议壳子（暂不选择）

- 扩大帧长度，或新增专用同步帧；
- 保留现有确认容量；
- 但这已经不是 `T07` 内的小改，而是新一轮协议修订。

当前前提已经明确：选择方案 A，并将字段命名收束为 `LMT_A/LMT_D`。`T11` 已完成，后续继续推进 `T07` 的全网统一结束时刻与多网关取舍验证。
