# 自组网协议状态转移深度拆解

> 目的：统一当前对协议状态转移的理解，作为后续实现、审查和联调时的对照基准。
> 范围：只描述协议层状态、帧触发条件和数据流闭环；链路层发射、接收、退避和硬件休眠只作为外部条件提及。

## 1. 约束来源与当前解释

1. 最高协议约束仍以 `docs/智能巡查系统自组网协议-003.pdf` 为准。
2. 当前工程设计参考 `docs/软件设计文档.md`、`docs/设计文档（初稿）.md` 和 `docs/任务分解技术书.md`。
3. 本文按照当前已实现的 `Ad-Hoc-lib` 行为拆解状态转移，主要实现锚点为：
   - `lib/Ad-Hoc-lib/src/adhoc_sm.c`：A 类组网状态机。
   - `lib/Ad-Hoc-lib/src/adhoc_data_plane.c`：D 类数据面、去重、转发、ACK。
   - `lib/Ad-Hoc-lib/src/adhoc_node.c`：A/D 帧调度和任务层 API。
4. 本轮确认入网确认使用 `Flag=7`：子节点请求入网时仍使用绑定编号 `N(0..5)` 指向上级；上级确认时统一写入 `ID(flag=7, 子节点ID)`。
5. 因此本文按 `Flag=7` 确认模型展开；当前主分支代码已完成从 `Flag=N` 判定到 `Flag=7` 判定的收口。

## 2. 基础术语

| 名称 | 含义 |
| ---- | ---- |
| 网关 | `Level=0` 的组网发起方，负责广播 0 级 A 帧、收集入网请求、发送确认、接收 D 数据并发送 D ACK。 |
| 上级 | 当前节点选择的父节点，可以是网关，也可以是已确认的上一级信标。 |
| 下级 | 请求加入当前节点所在方向的子节点。 |
| 方向 | 由 `gateway_no + upstream_level + upstream_id` 确定的上行路径。多网关场景中同一时刻只锁定一个方向。 |
| 绑定编号 `N` | `0..5`，子节点针对某个上级分配的本地编号；仅用于入网请求和后续转发编号，不作为入网确认回显位。 |
| `Flag=6` | 已确认节点广播本级别 A 帧时，用于声明自己的已确认上级 ID。它不是对子节点的确认。 |
| `Flag=7` | 入网确认标记；上级确认下级入网时写入 `ID(flag=7, 子节点ID)`。 |
| `LMT_A` | A 类帧 `Content[0..3]`，组网/管理时间字段。 |
| `LMT_D` | D 类数据帧 `Content[0..2]`，数据采样时间，同时作为数据唯一键的一部分。 |

## 3. 帧字段与状态触发点

### 3.1 A 类帧

A 类帧用于组网、入网请求、确认和已确认节点广播。

| 场景 | `msg_class` | `Level/V` | `Sender/S` | `Content` |
| ---- | ----------- | --------- | ---------- | --------- |
| 网关广播 | A | `0` | 网关 ID | `LMT_A(4B) + ID(flag=7, 子节点ID) x 0..4 + 0填充` |
| 信标入网请求 | A | `n` | 信标自身 ID | `LMT_A(4B) + ID(flag=N, 上级ID) + 0填充` |
| 已确认信标广播 | A | `n` | 信标自身 ID | `LMT_A(4B) + ID(flag=6, 已确认上级ID) + ID(flag=7, 子节点ID) x 0..3 + 0填充` |

关键解释：

1. `Level=0` 只由网关发出。
2. `Level=n(n>=1)` 可以是未确认节点的入网请求，也可以是已确认节点的本级广播；接收方需要结合 `Content` 中目标 ID 和 `Flag` 判断。
3. 入网请求中的 `ID(flag=N, 上级ID)` 表示“我正在用编号 `N` 请求加入这个上级”。
4. 确认中的 `ID(flag=7, 子节点ID)` 表示“这个子节点被上级确认入网”。
5. `Flag=6` 只表示“我的已确认上级是谁”，下级收到后可用于确认方向存在，但不能把它当成自身确认。

### 3.2 D 类帧

D 类帧用于数据上行和网关 ACK。

| 场景 | `msg_class` | `Level/V` | `Sender/S` | `Content` |
| ---- | ----------- | --------- | ---------- | --------- |
| 数据原发/转发 | D | `n(n>=1)` | 当前发送者 ID | `LMT_D(3B) + 源ID(4B) + 用户数据(17B)` |
| 网关 ACK | D | `0` | 网关 ID | `(源ID(4B)+LMT_D(3B)) x 0..3 + 0填充(3B)` |

关键解释：

1. 数据唯一键为 `源 node_id + LMT_D`，不把会随转发改变的 `id_flag` 计入唯一键。
2. 网关 ACK 只由网关发出；中继节点当前不生成下行逐级 ACK。
3. 多跳中的“链路内确认”主要依赖监听同一 `源 node_id + LMT_D` 被上级继续转发。

## 4. 网关到节点：组网广播与确认链路

### 4.1 网关内部状态

网关没有使用 `ST1/U1/C1` 这组信标状态，而是按组网窗口运行：

| 网关状态 | 进入条件 | 行为 | 退出条件 |
| -------- | -------- | ---- | -------- |
| 未启动 | 初始化或复位后 | 等待第一次 `poll` | 第一次 `poll` 时进入组网窗口 |
| 组网窗口开启 | `gateway_network_started=1` | 每个 `T5` 周期发送 `A,V=0`，发送后开启 `T2` 收集窗口 | `network_window_us` 到期 |
| `T2` 收集 | 发送一次 `A,V=0` 后 | 只接收当前 `T2` 窗口内的 A 类入网请求 | `T2` 到期 |
| 组网锁定 | 组网窗口到期 | 停止 `A,V=0`，关闭 `T2` 收集 | 复位或重组网策略重新拉起 |

### 4.2 网关广播 `A,V=0`

网关在 0 级广播中承担两个角色：

1. 宣告 0 级方向存在，供 `ST1` 信标发现。
2. 携带上一轮 `T2` 收集到的子节点确认列表。

发送内容：

```text
A,V=0,S=GW,Content=LMT_A + ID(flag=7, child_id) x 0..4 + 0填充
```

状态影响：

1. 对未入网信标：作为候选上级输入邻居表。
2. 对已进入 `U1` 的信标：若确认列表命中 `ID(flag=7, node_id=自身ID)`，进入 `C1`。
3. 对其他网关方向或其他上级的信标：不应改变当前锁定方向。

### 4.3 网关接收入网请求

网关只在 `T2` 收集窗口内处理入网请求。

接收过滤条件：

| 条件 | 不满足时的处理 |
| ---- | -------------- |
| 当前处于 `gateway_rx_window_open` | 忽略 |
| `msg_class=A` | 忽略 |
| `Level>0` | 忽略 |
| `Sender` 属于合法信标 ID 范围 | 忽略 |
| `Content` 中存在 `ID(flag=0..5, node_id=本网关ID)` | 否则继续检查 `Flag=6` 或忽略 |

命中入网请求后：

1. 取出 `matched_flag=N`。
2. 将 `ID(flag=7, node_id=请求信标ID)` 写入网关确认队列。
3. 下一次网关 `A,V=0` 时打包发送。

不产生确认的情况：

1. 请求不在 `T2` 窗口内。
2. 请求目标不是本网关 ID。
3. 请求中只有 `Flag=6`。
4. 请求中的 `Flag` 超出 `0..5`。
5. 同一节点重复请求只更新或去重，不扩大确认列表语义。

### 4.4 信标从网关广播进入 `U1`

信标在 `ST1` 中扫描 `A,V=0`：

1. 先检查 `domain_id`、`gateway_no`、`Level=0`、发送者 ID 合法性。
2. 将候选写入 Top-K 邻居表。
3. 按优先级比较：信号等级高、RSSI 高、上级级别低、`gateway_no` 小、上级 ID 小。
4. 候选达到信号命中规则后，分配或复用 `upstream_no=N`。
5. 状态从 `ST1` 进入 `U1`。

进入 `U1` 后信标记录：

| 字段 | 含义 |
| ---- | ---- |
| `joined_level=1` | 预计成为 1 级节点。 |
| `upstream_id=网关ID` | 当前选择的上级。 |
| `upstream_gateway_no` | 当前方向网关号。 |
| `upstream_no=N` | 针对该上级的绑定编号。 |
| `network_lock_end_us` | 当前方向的组网结束时间，本地推导。 |

### 4.5 `U1` 到 `C1`

`U1` 只接受当前上级对自身 ID 的 `Flag=7` 确认。

必须同时满足：

1. 收到 A 类帧。
2. `gateway_no == upstream_gateway_no`。
3. `sender.node_id == upstream_id`。
4. `event.level + 1 == joined_level`，对 1 级入网即上级 `Level=0`。
5. `Content[4..23]` 中存在 `ID(flag=7, node_id=自身ID)`。

满足后：

1. `U1 -> C1`。
2. 清零重试计数。
3. 启动或延续本方向锁定计时。
4. 开始周期广播 `A,V=1`，用于拉起下级。

明确不触发 `C1` 的情况：

1. `Flag=0..5`，即使 `node_id` 命中自身。
2. `Flag=6`。
3. `node_id` 命中但 `Flag` 不是 `7`。
4. 节点 ID 命中但网关号、上级 ID 或上级级别不匹配。
5. 来自更优但未被当前状态选中的其他网关方向的确认。

## 5. 节点到网关：入网请求与上行数据链路

### 5.1 信标发送入网请求

`U1/UN` 中，信标每个 `T5` 周期最多发送一次入网请求，最多 `retry_max` 次，当前默认 `30`。

1 级请求：

```text
A,V=1,S=Beacon,Content=LMT_A + ID(flag=N, node_id=网关ID) + 0填充
```

n 级请求：

```text
A,V=n,S=Beacon,Content=LMT_A + ID(flag=N, node_id=上级信标ID) + 0填充
```

失败回退：

1. 连续 `30` 周期未收到 `Flag=7` 确认，回退 `ST1`。
2. 未锁定结束前连续 `3*T5` 未收到当前上级 A 帧，回退 `ST1`。
3. 当前方向组网窗口到期但仍未确认，回退 `ST1`。

### 5.2 已确认信标广播给下级

已确认信标在 `C1/CN` 中承担“中继上级”和“下级确认者”双重角色。

发送内容：

```text
A,V=n,S=Beacon,Content=LMT_A + ID(flag=6, upstream_id) + ID(flag=7, child_id) x 0..3 + 0填充
```

状态影响：

1. 对未入网下级：该帧是候选上级信标。
2. 对已请求加入该节点的下级：该帧携带下级定向确认。
3. 对当前节点自身：周期发送该帧代表自己仍处于确认态并保持本级别广播。

注意：

1. `Flag=6` 固定占用一个 ID 槽，因此已确认信标单帧最多再确认 4 个下级。
2. 如果当前没有下级确认，也应保留 `Flag=6` 上级声明，供下级判断方向链路有效。
3. 组网窗口锁定后，已确认信标停止本级别广播；数据面是否继续可用由后续设计决定。

### 5.3 n 级节点加入上级信标

n 级加入与 1 级加入同构，只是上级由网关变成 `n-1` 级已确认信标。

状态转移：

```text
ST1 --发现 A,V=n-1 且候选达标--> UN
UN --收到当前上级 ID(flag=7,self_id)--> CN
UN --30周期无确认/上级失效/窗口到期--> ST1
CN --重组网到期/上级失效--> ST1
```

上级信标接收下级请求的过滤条件：

1. 自身已处于 `C1/CN`。
2. 本地组网窗口未关闭。
3. 下级请求的 `gateway_no` 等于自身锁定的 `upstream_gateway_no`。
4. 请求 `Level == 自身 joined_level + 1`。
5. `Content` 中存在 `ID(flag=0..5, node_id=自身ID)`。

命中后，将 `ID(flag=7, child_id)` 放入下级确认队列，后续广播带出。

## 6. 节点到网关：D 类数据状态转移

D 类数据不是 `ST1/U1/C1` 的替代状态，而是已确认组网状态上的叠加数据面。

### 6.1 数据源提交

应用层只在信标已确认并有有效上级时提交数据：

```text
adhoc_node_submit_data(node, source_id_flag, lmt_d, user[17], now_us)
```

协议帧：

```text
D,V=joined_level,S=当前节点ID,Content=LMT_D + ID(flag=source_id_flag, source_node_id) + user[17]
```

当前最小实现中，应用层默认 `source_id_flag=0`。完整多上级编号语义仍需后续继续收口。

### 6.2 中继接收与转发

中继收到 D 数据后先判断该帧是否是网关 ACK；若不是 ACK，则按数据帧处理。

数据帧处理顺序：

1. 校验 `msg_class=D`、`domain_id`。
2. 解出 `LMT_D`、源 ID、用户数据。
3. 用 `source.node_id + LMT_D` 查重。
4. 非重复数据写入去重表。
5. 如果本节点不是网关且具备有效上行路由，则准备转发。

转发规则：

| 接收数据来源 | 转发条件 | 转发时源 ID 的 flag |
| ------------ | -------- | ------------------- |
| 原发数据，`Sender == source.node_id` | 本节点已确认且有上级 | 改写为本节点 `upstream_no` |
| 转发数据，`Sender != source.node_id` | 收到数据的 `source.id_flag == 本节点 upstream_no` | 保持或改写为本节点 `upstream_no` |
| 不符合当前上行编号 | 不转发 | 不变 |

转发帧：

```text
D,V=本节点joined_level,S=本节点ID,Content=LMT_D + ID(flag=本节点upstream_no, source_node_id) + user[17]
```

### 6.3 监听确认

节点发送或转发某条数据后，会继续监听空口中的同源数据。

如果它收到上级或其他节点继续转发同一条数据：

```text
same_key = source.node_id 相同 && LMT_D 相同
```

则认为本跳已经被上级接收并继续处理，本地可以清理该条待发送数据并上报 `ACKED`。

这不是网关 ACK，而是链路内确认。它的意义是减少多跳场景中每一级都等待网关 ACK 的依赖。

### 6.4 网关接收数据并 ACK

网关收到 D 数据：

1. 解出 `source.node_id + LMT_D`。
2. 去重；重复数据不重复交付，但仍可保留 ACK 行为以帮助下游停止重发。
3. 将 `ID(source) + LMT_D` 放入 ACK 队列。
4. 按 `T5` 节拍最多打包 3 条 ACK。

网关 ACK 帧：

```text
D,V=0,S=GW,Content=(ID(source)+LMT_D) x 0..3 + 0填充
```

信标收到网关 ACK：

1. 只处理 `Level=0` 且 `Sender` 是网关 ID 范围的 D 帧。
2. 扫描最多 3 条 ACK。
3. 若任一 ACK 命中自身待发送队列中的 `source.node_id + LMT_D`，清理该条数据。
4. 通过 TX Report 通知应用层 `ACKED`。

### 6.5 数据失败状态

数据发送失败不改变组网状态，但会影响应用层观测：

| 条件 | 结果 |
| ---- | ---- |
| 队列已满 | `adhoc_node_submit_data()` 返回 busy。 |
| 未确认或无有效路由 | `adhoc_node_submit_data()` 返回 state skip。 |
| 每 `T5` 重发一次，达到 `retry_max` | 清理该数据，TX Report 为 `RETRY_EXHAUSTED`。 |
| 收到网关 ACK 或监听到上级转发 | 清理该数据，TX Report 为 `ACKED`。 |

## 7. 全局状态转移表

| 当前状态 | 输入/事件 | 条件 | 下一状态 | 备注 |
| -------- | --------- | ---- | -------- | ---- |
| `ST0` | 外部唤醒 | 上电、振动或应用触发 | `ST1` | 当前协议库不主动管理深睡眠。 |
| `ST1` | 收到 `A,V=0` | 候选达标，选择网关 | `U1` | 记录 `upstream_no=N`。 |
| `ST1` | 收到 `A,V=n-1` | 候选达标，选择上级信标 | `UN` | `joined_level=n`。 |
| `U1` | 发送入网请求 | 每 `T5` 一次，未超重试 | `U1` | `Flag=N` 指向网关 ID。 |
| `UN` | 发送入网请求 | 每 `T5` 一次，未超重试 | `UN` | `Flag=N` 指向上级信标 ID。 |
| `U1` | 收到 `A,V=0` | `ID(flag=7,self_id)` 命中 | `C1` | 必须来自当前网关。 |
| `UN` | 收到 `A,V=n-1` | `ID(flag=7,self_id)` 命中 | `CN` | 必须来自当前上级。 |
| `U1/UN` | 重试耗尽 | `retry_count >= retry_max` | `ST1` | 清除上级选择。 |
| `U1/UN` | 上级失效 | 连续 `3*T5` 未见当前上级 A 帧 | `ST1` | 只在网络锁定前触发。 |
| `U1/UN` | 方向窗口到期 | 未确认且到期 | `ST1` | 防止窗口后继续请求。 |
| `C1` | 周期发送 | 未锁定、未重组网 | `C1` | 发送 `A,V=1`。 |
| `CN` | 周期发送 | 未锁定、未重组网 | `CN` | 发送 `A,V=n`。 |
| `C1/CN` | 收到下级请求 | 同方向且目标为自身 | `C1/CN` | 加入确认队列。 |
| `C1/CN` | 上级失效 | 连续 `3*T5` 未见当前上级 A 帧 | `ST1` | 释放方向锁定。 |
| `C1/CN` | 重组网到期 | `regroup_interval_us` 到期 | `ST1` | 当前工程默认关闭。 |
| `C1/CN` | 组网窗口到期 | 本地方向锁定到期 | `C1/CN` | 停止 A 广播，保持已确认语义。 |
| 已确认状态 | 提交 D 数据 | 有有效路由 | 已确认状态 | 数据面排队发送。 |
| 已确认状态 | D ACK/监听确认 | `source.node_id + LMT_D` 命中 | 已确认状态 | 清理数据队列。 |

## 8. 明确忽略的输入

下列输入不应造成状态跃迁：

1. 任意状态下收到 `domain_id` 不匹配的帧。
2. `U1/UN` 中收到非当前 `gateway_no` 的确认。
3. `U1/UN` 中收到非当前 `upstream_id` 的确认。
4. `U1/UN` 中收到 `ID(flag=0..5,self_id)`。
5. `U1/UN` 中收到 `ID(flag=6,self_id)`。
6. `U1/UN` 中收到 `ID(flag=7,self_id)`，但来源不是当前 `gateway_no/upstream_id/level`。
7. 网关不在 `T2` 收集窗口内收到的入网请求。
8. 已确认节点锁定后收到的非当前方向下级请求。
9. D 数据中 `source.node_id + LMT_D` 已在去重窗口内处理过的重复业务数据。

## 9. 实现风险清单

1. 文档与代码已统一为 `Flag=7` 入网确认；请求绑定编号 `N(0..5)` 仅用于请求阶段，不作为确认命中位。
2. `docs/软件设计文档.md` 与当前实现在 D ACK 上已对齐为 `ID+LMT_D(7B)`。
3. `docs/软件设计文档.md` 与当前实现在去重键上已对齐为 `source.node_id + LMT_D`。
4. `LMT_A` 的绝对时间同步语义仍需要和 RTC/北斗时间源对齐；当前实现使用本地 `now_us` 推导。
5. 组网窗口结束后“已确认节点是否继续数据转发”需要明确。当前文档描述的是停止 A 类广播，不等于自动停止 D 类数据面。
6. 多网关场景尚需三板以上验证：同一节点同时收到两个网关方向时，必须验证 Top-K 选择、方向锁定、错误方向确认忽略。
7. 当前网关 ACK 不做逐级下发，中继链路依赖监听确认；如果实际链路拓扑导致下级听不到上级转发，需要补充逐级 ACK 或应用层容错策略。

## 10. 后续实现对照原则

1. 修改状态机前，先判断该行为属于 A 类组网状态，还是 D 类数据面状态。
2. A 类状态跃迁必须同时校验 `gateway_no + upstream_id + level + flag + node_id`。
3. D 类去重和确认必须只使用 `source.node_id + LMT_D` 作为唯一键。
4. `Flag=6` 只能表达“已确认上级”，不能进入确认队列，也不能触发 `U1/UN -> C1/CN`。
5. 组网窗口、重试上限、上级失效是三条独立退出路径，不能互相替代。
6. 多网关逻辑只能在 `ST1` 候选选择阶段切换方向；进入 `U1/UN/C1/CN` 后，除显式回退或重组网外不切换方向。
