# 智能巡查系统自组网协议 — 从设计到代码

> 面向读者：希望理解协议实现逻辑的开发者。不要求先读规范 PDF。

---

## 一、这个协议解决了什么问题

想象一个场景：几十个传感器散布在几公里的巡查路线上，每个传感器采集温湿度、加速度，需要把数据传回一台主机（网关）。没有 WiFi、没有 4G，只有 2.4GHz 的微弱射频——而且电池供电，不能一直开着接收。

这就是自组网协议要解决的问题：**用最少的电量、最简单的射频，把多级节点的数据逐跳传到网关**。

## 二、物理帧——32 字节的"信鸽"

协议栈的一切都围绕一个 32 字节的固定帧展开。32 字节很小——大约是一条短短信的长度，但已足够承载组网和数据的全部信息。

```
地址  0      1      2          7                     31
     +------+------+----------+---------------------+------+
     |Header|Level |  Sender  |  Content (24字节)    | CRC8 |
     +------+------+----------+---------------------+------+
       1B     1B      5B                                1B
```

把每一帧想象成一封信：

| 字段 | 相当于 | 内容 |
|------|--------|------|
| Header | 信封颜色 | 区分"组网信令"还是"数据"，以及来自哪个网关方向、在哪个时隙发出 |
| Level | 楼层号 | 0=网关，1=第一层信标，2=第二层信标…… |
| Sender | 寄信人 | 谁的域号（哪个网络）+ 谁的节点 ID |
| Content | 信纸内容 | 24 字节——根据帧类型不同，放时间戳、ID 列表、用户数据 |
| CRC8 | 封蜡 | 校验整封信没有破损 |

**为什么固定 32 字节？** 因为射频芯片一次只能发固定长度的包，协议栈不做变长处理，可以避免动态内存、碎片、边界判断——在资源极少的单片机上，固定就是安全。

### 2.1 Header 字节的拆分

一个字节 8 个 bit，被拆成了三段：

```
bit7         bit6-4       bit3-0
+--------+--------------+-----------+
| A还是D | 网关编号 0~7  | 时隙高4位 |
+--------+--------------+-----------+
```

- **A/D**：A 帧（组网信令）和 D 帧（业务数据）用同一条射频通道，靠这个 bit 区分。状态机收到帧后，A 帧进 A 帧处理逻辑，D 帧进数据面。
- **网关编号**：允许同时存在多个网关，信标靠这个字段知道"这封 A 帧来自哪个网关方向"。
- **时隙高 4 位**：配合一个底层 8 位计数器凑成 12 位时隙号。时隙号的最低位必须和 Level 的最低位相同奇偶——这是用 parity 做层间隔离，偶数层用偶数时隙，奇数层用奇数时隙，相邻层的帧在空中就不会撞。

### 2.2 Sender 字段——5 字节的"身份证"

Sender = 域号（11 bit）+ 节点 ID（29 bit），总共 40 bit = 5 字节，大端存储。

域号让多个自组网可以在同一空口中互不干扰；节点 ID 分两段——`≤1000000` 的是网关，`≥1000001` 的是信标。状态机收到一帧后，先看 Level：如果 Level=0，Sender 的 ID 必须在网关范围内；如果 Level≥1，ID 必须在信标范围内，否则丢弃。这是一个简单的范围校验。

### 2.3 Content——"信纸"上的 24 字节

Content 是帧中最灵活的部分。时间戳不再占独立的帧位置，而是放在 Content 的最前面。

| 帧类型 | Content 布局 |
|--------|-------------|
| A V=0（网关广播） | `LMT_A(4B) + 确认列表 flag=7 × 5 ×4B` = 24B |
| A V=n（入网请求） | `LMT_A(4B) + 上级ID flag=0~5(4B) + 确认列表×4` |
| A V=n（已确认广播） | `LMT_A(4B) + 已确认上级 flag=6(4B) + 确认列表 flag=7 ×4` |
| D V=n（数据消息） | `LMT_D(3B) + 数据源ID(4B) + 用户数据(17B)` = 24B |
| D V=0（网关 ACK） | `(source.id + LMT_D) × 3 条 × 7B + 0填充(3B)` |

## 三、六个状态的"人生轨迹"

协议的状态机是理解一切的关键。一个信标节点从开机到稳定工作，经历了 6 个状态：

```
ST0(深度休眠) → ST1(等待组网) → U1/UN(未确认) → C1/CN(已确认)
```

### 3.1 ST1——"我醒了，看看周围有没有人"

`adhoc_sm_enter_st1()` 清空一切：上级信息、邻居缓存、确认队列全部归零。然后进入被动监听。

在 ST1 中，节点交替执行 T3（侦听）+ T4（休眠）。T3 期间收到 A 帧后，`adhoc_sm_neighbor_record()` 把发送者记入"邻居缓存"——一个 Top-K 槽位数组，容量为 6。核心逻辑：

1. 先看这个发送者的 RSSI：≥-65 dBm 是强信号，≥-80 是中信号，其余是弱信号
2. 根据信号等级设定期望命中次数和评估窗口：强需 1 次/1 周期，中需 1 次/2 周期，弱需 2 次/4 周期
3. 记录该邻居的命中次数，每个 T5 周期最多计一次
4. 定时扫描过期邻居——太久没新命中的就从缓存中清除

当 `adhoc_sm_select_best_ready_neighbor()` 发现某个邻居的命中次数达标且未过期，就把它选为候选上级，从 ST1 跳转到 U1（上级是网关）或 UN（上级是信标）。

### 3.2 U1/UN——"我选好了上级，请求入网"

进入未确认态后，`adhoc_sm_emit_join_response()` 每 T5 周期向选定的上级发一封入网请求：

```
A V=n, Content = LMT_A + 上级ID(flag=自身绑定编号 0~5) + 下级确认列表
```

同时监听上级的回复。上级收到请求后，调用 `adhoc_reply_list_push_confirm_unique()` 把请求者放入确认队列——**自动设置 flag=7**。

下级收到上级的 A 帧后，`adhoc_sm_content_has_confirm_self()` 扫描 Content 中所有 ID 条目，找 "flag=7 且 node_id=自己" 的那一条。命中了就 `enter_cn()`，转入已确认态。

如果 30 个周期没被确认（`retry_max`），或者上级"失联"超过 3×T5（`upstream_loss_timeout_us`），回退 ST1 重来。

### 3.3 C1/CN——"我入网了，现在我是中继站"

已确认态下，`adhoc_sm_emit_level_beacon()` 每 T5 周期广播本级别信标：

```
A V=n, Content = LMT_A + 已确认上级(flag=6) + 下级确认列表(flag=7)
```

同时持续接收：
- 如果收到更下级（level = n+1）的入网请求 → 加入确认队列，回复 flag=7 确认
- 如果连续 3×T5 没收到上级信标 → 回退 ST1
- 如果组网窗口到期 → 停止广播 A 帧，但数据面继续工作
- 如果重组网定时器到期 → 回退 ST1 重新寻网

### 3.4 网关的特殊行为

网关在 poll 中走的是完全独立的分支：

1. 首次 poll 启动组网，记录 `network_start_us`，设定 `network_end_us`
2. 每 T5 周期发送 `A V=0`（slot=0），然后开启 `T2` 接收窗口
3. T2 窗口内收到 A 帧 → 从中解析 flag=0~5（绑定编号）的条目 → 加入确认队列 → 下次广播时以 flag=7 回复
4. 网络窗口超时 → `gateway_network_locked=1`，停止广播

## 四、时间系统——"LMT_A"和"LMT_D"是怎么算出来的

协议里有两个时间戳：LMT_A（挂在 A 帧里）和 LMT_D（挂在 D 帧里）。它们来自同一个微秒单调时基 `now_us`，但编码不同。

### 4.1 BDT 基线——"把单调微秒翻译成真实秒"

核心函数：`adhoc_time_set_bdt_base(mono_us, bdt_second)`

```
应用层调用流程:
  RTC 读出当前 BDT 秒 (2006-01-01 00:00:00 起算)
      ↓
  TMOS 给出当前 mono_us (系统启动以来的微秒计数)
      ↓
  adhoc_time_set_bdt_base(mono_us, bdt_second)
      ↓
  协议栈内部记录: s_bdt_base_valid = 1
                 s_bdt_base_mono_us = mono_us
                 s_bdt_base_second = bdt_second
```

之后任何 `now_us` 换算为秒：
```
BDT秒 = s_bdt_base_second + (now_us - s_bdt_base_mono_us) / 1000000
```

如果应用层没有调用 `set_bdt_base`，`s_bdt_base_valid` 保持为 0，时间戳退化为 `now_us / 1000000`——单调微秒除以 1e6，成为一个"伪秒"。**协议正确性不受影响**，因为去重用 LMT_D 作为唯一键，只要同一个源发出的 LMT_D 单调递增即可。

### 4.2 LMT_A——A 帧的时间戳（4 字节）

LMT_A 编码了 **秒** 和 **秒内的 T5 周期编号**：

```
LMT_A = (秒 % 2^25) | ((秒内微秒 / T5) << 25)
        └─ 25bit ─┘    └──── 7bit ───────────┘
```

- 秒字段（25bit）可以表示约 388 天，远超协议需求
- 周期字段（7bit）表示当前秒内的第几个 T5（0~127）

接收方拿到 LMT_A 后，结合 Header 中的时隙号，可以推算出帧发出的精确时刻——这在时间同步和延迟测量中非常关键。

### 4.3 LMT_D——D 帧的时间戳（3 字节）

LMT_D 是纯秒级时间戳，取 BDT 秒的低 24 位，直接用作数据唯一条目标识符：

```
LMT_D = BDT秒 & 0x00FFFFFF
```

因为 D 帧最多重试 30 个 T5 周期（约 1.8 秒），而 24 位秒的跨度约 194 天——远大于任何合理的数据生命周期，冲突概率为零。

## 五、数据面——从传感器到网关的"接力赛"

### 5.1 提交数据

应用层调用 `adhoc_node_submit_data(node, id_flag, lmt_d, user[17], now_us)`。如果 `lmt_d=0`，协议栈自动调 `adhoc_lmt_d_from_us(now_us)` 生成。

数据被包装成 `adhoc_data_msg_t`（包含 source 标识 + LMT_D + 17 字节用户数据）放入 `tx_queue`（环形队列，容量 16）。

### 5.2 发送与重试

`adhoc_data_plane_poll_forward_tx()` 每 T5 周期扫描 `tx_queue`，取出到期的待发条目，组装 D 帧发送。`retry_count` 自增，每 T5 发送一次，直到：
- 收到网关 ACK → 清理条目，报告 `ACKED`
- 监听到上级转发 → 清理条目，报告 `ACKED`
- 重试达到 30 次 → 清理条目，报告 `RETRY_EXHAUSTED`

### 5.3 去重

收到 D 帧后，查去重表（64 槽，环形 LRU）。去重键 = `source.node_id + LMT_D`。同一键在 6 小时内只处理一次。命中去重表 → 标记为重复，不重复交付应用层。

### 5.4 监听确认——"看上级有没有继续转发"

这是协议最巧妙的设计：发送节点发出数据后并不等待明确的 ACK，而是**继续监听空中**。如果听到上级向更上级转发同一条数据（相同的 `source.node_id + LMT_D`），说明上级已收到并处理了——这就够了。

这个"零开销确认"依赖一条拓扑假设：**沿着同一路径，下级能听到上级向更上级发送的帧**。组网阶段的三次握手（信号判定 → 入网请求 → flag=7 确认）已经验证了这条路径是可靠的，所以监听确认是"借用已验证链路的信任"。

### 5.5 网关 ACK——"官方确认"

网关收到 D 帧后，将 `source_id + LMT_D` 放入 `ack_queue`。按 T5 节拍打包最多 3 条 ACK 到 D 帧中广播。任何收到这条 ACK 帧的节点——不管中间隔了几跳——只要在 ACK 列表中看到自己的数据标识，就可以清理。

网关 ACK 不做逐级下发（中继不转发网关的 ACK）。这是精心选择的——避免每一跳都增加空中帧流量。源节点直接从网关 ACK 获得确认（如果它在网关的射频覆盖范围内的话），否则依靠监听确认。

## 六、确认队列——"A 帧里的 flag=7 是怎么来的"

`adhoc_reply_list_t` 是一个环形 FIFO，容量 24。它只做一件事：收集需要确认的节点 ID，然后在下次广播 A 帧时打包发出。

关键函数 `adhoc_reply_list_push_confirm_unique(node_id)`：
1. 自动设置 `id_flag = 7`
2. 按 `node_id` 去重——如果队列里已有此 ID，更新 flag（保证永远是 7）
3. 按 FIFO 追加到队尾

`adhoc_reply_list_build_confirm_payload(list, content, offset, max_ids)` 从队头弹出最多 `max_ids` 个条目，统一写为 `flag=7`，打包到 Content 的指定偏移位置。

网关和信标的逻辑是一样的——只不过网关最多打包 5 条（因为 Content 前 4B 是 LMT_A，剩下 20B = 5×4B），信标最多打包 4 条（因为 Content 前 4B 是 LMT_A，第 5~8 字节是已确认上级 ID，剩下 16B = 4×4B）。

## 七、接口设计——"谁调用谁"

### 7.1 应用层 → 协议栈

| 函数 | 什么时候调用 | 作用 |
|------|-------------|------|
| `adhoc_node_init(mem, cfg, link_ops)` | 系统启动一次 | 分配内存、初始化状态机+数据面+时序 |
| `adhoc_node_set_role(node, GATEWAY/BEACON)` | 启动时 | 设定本节点是网关还是信标 |
| `adhoc_node_poll(node, now_us)` | 每 5ms（TMOS 事件） | 推进状态机、处理重试、生成待发帧 |
| `adhoc_node_on_rx(node, rx)` | RF 收到帧的回调 | 将空中帧注入协议栈（A 帧进状态机、D 帧进数据面） |
| `adhoc_node_fetch_tx(node, tx)` | poll 之后 | 取出协议栈生成的待发帧，交给 RF 发送 |
| `adhoc_node_submit_data(node, lmt_d, user)` | 传感器有数据时 | 提交 17 字节用户数据到发送队列 |
| `adhoc_node_fetch_data_tx_report(node, report)` | 周期性查询 | 获取数据发送结果（已确认 / 重试耗尽） |

### 7.2 协议栈 → 链路层（回调）

`adhoc_link_ops_t` 是五个函数指针，由应用层实现：

| 函数指针 | 作用 |
|----------|------|
| `init()` | 初始化 RF 硬件 |
| `set_channel(ch)` | 切换频道（协议栈不感知信道） |
| `send(frame, len, when_us)` | 发送 32 字节帧（立即或定时发送） |
| `enable_rx(duration_us)` | 开启接收窗口 |
| `get_ts_us()` | 获当前单调微秒时间戳 |

## 八、一个信标的完整入网之旅

作为总结，我们跟踪一个信标从开机到开始上传数据的全过程：

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. ST0 → ST1                                                    │
│    adhoc_node_init() → enter_st1()                              │
│    所有状态归零，开始被动监听                                      │
├─────────────────────────────────────────────────────────────────┤
│ 2. ST1 阶段                                                      │
│    T3=62.5ms 侦听 → T4=1937.5ms 休眠 → 循环                       │
│    收到网关 A V=0 帧 → RSSI=-55 (强信号)                           │
│    → neighbor_record(gateway, signal_rank=3, required_hits=1)    │
│    → 网关命中次数达标 → select_best_ready_neighbor() 选中          │
│    → enter_un(joined_level=1) → 转入 U1                          │
├─────────────────────────────────────────────────────────────────┤
│ 3. U1 阶段                                                       │
│    每 T5=60ms 发送入网请求:                                       │
│    A V=1 Content = LMT_A + 上级ID(flag=0, gateway_id)             │
│    网关收到请求 → push_confirm_unique(b1_node_id) [flag=7]        │
│    网关下次广播 A V=0 → Content 中携带 (flag=7, b1_node_id)       │
│    信标 → content_has_confirm_self() 命中 → enter_cn()            │
│    → 转入 C1                                                     │
├─────────────────────────────────────────────────────────────────┤
│ 4. C1 阶段                                                       │
│    每 T5=60ms 广播 A V=1 信标:                                    │
│    Content = LMT_A + 已确认上级(flag=6) + 确认列表(flag=7)         │
│    接收更下级(B2)的入网请求 → 确认 → B2 入网                        │
│    接收 B2 发来的 D 帧 → 监听 B2 是否向网关转发 → 若转发则清理      │
│    传感器有数据 → submit_data(user[17]) → 组装 D V=1 → 发给上级     │
├─────────────────────────────────────────────────────────────────┤
│ 5. 异常回退                                                       │
│    任何时刻:                                                      │
│    - 重试 30 次未确认 → 回退 ST1                                   │
│    - 连续 3×T5 未收到上级信标 → 回退 ST1                            │
│    - 组网窗口到期 → 停止 A 广播，数据面继续                         │
│    - 重组网定时器到期 → 回退 ST1 重新寻网                           │
└─────────────────────────────────────────────────────────────────┘
```
